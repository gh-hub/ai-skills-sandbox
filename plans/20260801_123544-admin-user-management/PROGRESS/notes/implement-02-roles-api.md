# Implement notes: 02 — Roles API

## What was built

A new `RolesModule` at `apps/api/src/apps/roles/`, mirroring the existing `AwardsModule` structure (controller + service + repository + util + dto/):

- `apps/api/src/apps/roles/roles.repository.ts` — `findAll`, `findById`, `findByName`, `insertRole(name)` (always inserts `isBuiltIn: false`), `findHoldersByRoleId(roleId)` (join `user_roles` → `users`, returns `{name, email}[]`), `deleteRoleAndClearHolders(roleId)` (deletes `user_roles` rows for the role, then the role row).
- `apps/api/src/apps/roles/roles.util.ts` — `toRoleDto` mapping a `RoleRow` to the shared `Role` type.
- `apps/api/src/apps/roles/roles.service.ts` — `getAll`, `create` (409 `ConflictException` on duplicate name, including built-in names since they're just rows with `isBuiltIn: true`), `remove(id, force)`:
  1. 404 `NotFoundException` if the role id doesn't exist.
  2. 409 `ConflictException` if `role.isBuiltIn` — checked *before* the holders check, so force never overrides it.
  3. 409 `ConflictException` with body `{ message, users }` if held by users and `force` is not true — nothing is deleted in this branch.
  4. Otherwise calls `deleteRoleAndClearHolders` (safe to call even when there are zero holders — it's the same code path used for both "force" and "no one holds it" deletes).
- `apps/api/src/apps/roles/roles.controller.ts` — `GET /roles`, `POST /roles`, `DELETE /roles/:id?force=true`, all three gated with `@UseGuards(RolesGuard)` + `@Roles("ADMIN")` **per-method** (not at class level — `RolesGuard` reads metadata via `context.getHandler()` only, so a class-level `@Roles(...)` would silently do nothing; confirmed by reading `AwardsController`, which also decorates per-method).
- `apps/api/src/apps/roles/dto/`: `role.dto.ts`, `create-role.dto.ts`, `delete-role-query.dto.ts` (boolean `force` query param — needed a `@Transform(({value}) => value === true || value === "true")` since `@Type(() => Boolean)` on a query string coerces any non-empty string, including `"false"`, to `true`), `role-in-use.dto.ts` (swagger-only shape for the 409-in-use body).
- Registered `RolesModule` in `apps/api/src/app.module.ts`.
- Added to `packages/shared-types/src/index.ts`: `Role`, `CreateRoleRequest`, `RoleUserSummary`, `RoleInUseError`. **Rebuilt the package** (`npm run build` in `packages/shared-types`) — its `dist/` is what `apps/api` actually imports (`main`/`types` point at `dist/`), so editing only `src/index.ts` does not update consumers' typechecking until it's rebuilt.
- No new migration — ticket 01 already created the `roles` table with everything ticket 02 needed (`id`/`name`/`isBuiltIn`), and ADMIN/OPERATOR are already seeded as `isBuiltIn: true` in `apps/api/drizzle/0005_wooden_black_cat.sql`.

## Ambiguities resolved (not specified by the ticket, reasonable calls made)

- **HTTP status codes**: ticket text says "rejected as a conflict" for duplicate names and doesn't specify a code for built-in-delete-rejected or in-use-delete-rejected. Used `409 Conflict` uniformly for all three (name conflict, built-in-undeletable, in-use-blocked) to match the existing codebase precedent (`AuthService.signup` throws `ConflictException("Email already in use")` for its one conflict case) and because all three are "current state of the resource conflicts with the request," which is exactly what 409 means.
- **In-use-blocked response shape**: ticket says the response must "identify exactly which users (by name and email) are affected." Implemented as a JSON body `{ message: string, users: { name: string; email: string }[] }` on the 409 response (Nest's `HttpException` sends whatever object you pass it as the response body, no extra wiring needed). Added to shared-types as `RoleInUseError`/`RoleUserSummary` so ticket 04's frontend delete-confirmation modal can type against it directly.
- **`force` query param**: `DELETE /roles/:id?force=true`. Not specified by the ticket which transport (query vs. body) to use for a DELETE; query param is the only reasonable choice for a body-less DELETE and is what `apps/web`'s eventual delete-role-modal will call.

## Gotchas for the next ticket (03 — Users API)

- **The ADMIN lock is name-based, not `isBuiltIn`-based.** Both `ADMIN` and `OPERATOR` have `isBuiltIn: true` — ticket 03's "highest-privilege role can never be granted/revoked" rule must check `role.name === "ADMIN"` specifically, not `role.isBuiltIn`. (This module's built-in-delete-protection *is* correctly `isBuiltIn`-based, since both built-ins are meant to be permanently undeletable — that's a different rule from the ADMIN-grant lock ticket 03 needs.)
- **No cross-module import needed for role lookups.** `RolesModule` does not export `RolesRepository` (same as `AwardsModule` never exporting anything for `LikesModule` to use `likeAwards`). Ticket 03's `UsersRepository`/service should query the `roles` table directly via its own repository methods rather than importing `RolesModule` — that's the established convention in this codebase (modules reach into shared `schema.ts` tables directly rather than depending on each other's repositories).
- **Role shape available to the frontend**: `GET /roles` returns `Role[]` = `{ id: string; name: string; isBuiltIn: boolean }[]` (see `packages/shared-types`). Ticket 03's grant/revoke endpoints will presumably take a `roleId` (uuid) path or body param to match this — there is no role-by-name lookup route, so the frontend will need to fetch the role list first to get ids for its role-toggle UI (ticket 05).
- **`findRolesByUserId` (from ticket 01, unchanged)** still returns plain `string[]` role names — useful for building each user's inline roles list in ticket 03's `GET /users` response, but not useful for grant/revoke validation (which needs the role row, i.e. `id`/`isBuiltIn`/`name`, via a role-id lookup like this ticket's `RolesRepository.findById`).
- **Boolean query params need explicit `@Transform`.** `@Type(() => Boolean)` alone on a `class-transformer` DTO field coerces any non-empty query string (including `"false"`) to `true`. If ticket 03 adds any boolean query/body flags, use `@Transform(({ value }) => value === true || value === "true")` as done in `apps/api/src/apps/roles/dto/delete-role-query.dto.ts`.
- **`npm run generate:openapi` is currently broken in this local environment** (pre-existing, unrelated to this ticket): `nest build` doesn't emit `dist/generate-openapi.js`/it can't resolve relative requires when run standalone outside Docker. Did not chase this — out of scope for ticket 02, and the coding rules doc already flags Docker-build-specific gotchas for this repo. `apps/api/openapi.json` was **not** regenerated this session; ticket 04/05 (frontend) should be aware the OpenAPI spec doesn't yet reflect the new `/roles` routes, and `apps/web/lib/api-client/schema.d.ts` will need either a working Docker-based generation run or hand-written types for `roles.ts`.
- **Shared-types package must be rebuilt after editing `packages/shared-types/src/index.ts`** — `apps/api` and (presumably) `apps/web` resolve it via `dist/`, not `src/`. Run `npm run build` in `packages/shared-types` after any further edits there, or `tsc --noEmit` in consumers will show stale/missing-export errors that look like a typo.
