# Implement: 06 — Admin navigation

## What was built

- `apps/web/components/admin-nav-link.tsx` — new client component `AdminNavLink`: calls `useMe()`, renders `null` while loading, for an anonymous visitor, and for a logged-in non-admin (mirrors `AdminGate`'s exact check, `me.data.roles.includes("ADMIN")`); renders a `Link` to `/admin` labeled "Admin" only for a logged-in admin.
- `apps/web/app/layout.tsx` — added `<AdminNavLink />` to the real header (`<header className="flex items-center justify-end gap-4 px-6 py-4">`, which already held the "Awards" link and `ThemeToggle`). **Correction to CONTEXT.md/prior notes**: the header does *not* render `header-auth-control.tsx` — that component is only used inside the home page's mock-terminal-window bar (`apps/web/app/page.tsx`), not in the layout header. The header itself has no auth-awareness at all before this ticket, so a new small client component was the right shape rather than folding this into `header-auth-control.tsx`.
- `apps/web/app/admin/page.tsx` — new `/admin` hub page, wrapped in the existing `AdminGate` (reused as-is), with links to `/admin/users`, `/admin/roles`, and `/` (labeled "← Back to home", styled the same as the existing `← Back` convention on `apps/web/app/awards/page.tsx`).
- `apps/web/app/admin/roles/page.tsx` and `apps/web/app/admin/users/page.tsx` — each gained a "← Back to Admin" link at the top pointing to `/admin`, following the same styling convention.
- `apps/e2e/tests/admin-navigation.spec.ts` — new Playwright spec: header-link visibility for anonymous/non-admin/admin, admin clicking through to the hub, hub → each sub-page → back, and both sub-pages' back-link to the hub.

## Verification

- `npx tsc --noEmit` clean in both `apps/web` and `apps/e2e` (run after each meaningful change).
- `npm run build` in `apps/web` succeeds; new route `/admin` (781 B) prerenders as static alongside `/admin/roles` and `/admin/users`.
- **Live e2e — partial, with one real bug found and fixed, plus a separate environment issue hit along the way:**
  - First live run of the new spec: 2 of 5 tests passed (anonymous visitor doesn't see "Admin" link; logged-in non-admin doesn't see it), 3 failed — every test that signs up a user with an admin-name-derived email.
  - Root-caused this via the Playwright trace (`0-trace.network` + attached request/response bodies): the API returned `400 {"message":["email must be an email"],...}`. The generated email's **local-part exceeded 64 characters** — `class-validator`'s `@IsEmail()` (via `validator.js`) enforces the RFC 5321 64-char local-part limit by default. My original `uniqueEmail` used prefix `admin-navigation-e2e-` + a name-derived label + a full UUID, reliably producing a 70-80+ char local part.
  - **This corrects ticket 04's notes**, which attributed an identical failure pattern in `admin-roles-page.spec.ts` to a "harness boot race." I reproduced the exact same failure live on the *unmodified* `admin-roles-page.spec.ts` and `admin-users-page.spec.ts` and confirmed via the same trace method that it is this email-length bug, not a boot race — every admin-named test in both of those files' `uniqueEmail`/`loginAsAdmin` helpers also exceeds 64 chars and would fail live for the same reason. Not fixed here (out of scope for ticket 06, and all tickets are otherwise done) — logged as tech debt below.
  - Fixed it in my own new spec: `uniqueEmail` now uses a short `e2e-` prefix (`e2e-${label}-${randomUUID()}@example.com`), keeping every local part in this file under 64 chars. Confirmed the specific bug is gone: re-running showed `signup` now returning `201` for every admin-named test (traced directly against `web`'s access log), i.e. the actual application code is correct — the previous failures were 100% a test-data bug, not a bug in the navigation feature.
  - After that fix, a second, unrelated issue surfaced: the docker-compose e2e stack (already up for ~3 hours across this and prior sessions' live-verification runs) started intermittently refusing connections (`net::ERR_CONNECTION_REFUSED` mid-run) even though `docker compose ps` showed all three containers `Up`. I tore the stack down for a clean `docker compose up --build` retry; partway through that rebuild, the **Docker Desktop daemon itself** became unresponsive (`docker ps`/`docker info` returned `500 Internal Server Error` from the daemon's API, persisting after a 15s wait) and Playwright's `webServer` gave up after its 300s boot timeout. This is a sandbox/Docker-Desktop-level failure, not a code or test issue, and out of scope to troubleshoot further in this ticket.
  - **Net effect on acceptance criteria**: the header-link-visibility criterion is live-verified for its anonymous and non-admin cases (both passed against the real stack); its admin-visible case, plus both hub-navigation criteria, remain verified via `tsc --noEmit` + `next build` + code review (reused, already-verified `AdminGate` and the same `Link`/styling conventions already live-verified for `/admin/roles` and `/admin/users` in tickets 04/05) rather than a completed live e2e pass, purely because of the Docker Desktop outage above. Marked `[~]` rather than `[x]` on the ticket for that reason rather than silently checking it off.
- All other acceptance criteria in `tickets/06-admin-navigation.md` marked `[x]`; the e2e-hub-navigation one marked `[~]` with the reasoning above.
