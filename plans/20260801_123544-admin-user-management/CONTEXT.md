# Context: Admin User Management

## What we're building
An admin-only user/role management UI and API: an `/admin` hub with `/admin/users` (paginated, searchable user list with role grant/revoke) and `/admin/roles` (list/create/delete roles), gated to ADMIN only.

## Key decisions
- ADMIN-only access to all new surfaces, following the existing `RolesGuard` + `@Roles(...)` pattern; `POST /auth/signup` verified unaffected. See `grill/decisions.md`.
- `role` enum replaced by a real `roles` table with FK-based `user_roles.role_id` and a backfill migration; JWT/`AuthUser`/`RolesGuard` contracts unchanged. See `grill/ADR-001.md`.
- The `ADMIN` role can never be granted or revoked through this feature, for anyone, including an admin's own row — enforced server-side. See `grill/decisions.md`.
- Custom roles are pure labels with no enforcement wiring; only custom (non-built-in) roles are deletable, with block-by-default + force-flag deletion semantics. See `grill/decisions.md`.
- `GET /users` is paginated and searchable from the start, a deliberate deviation from this codebase's simple-list convention; response shape and default page size deferred to spec/tickets. See `grill/ADR-002.md`.

## Spec

## Gotchas
- The `roles` table has only `id`/`name`/`isBuiltIn` — no `createdAt`. If the `/admin/roles` list wants a creation date, that column doesn't exist yet and would need adding as part of ticket 04.
- Built-in roles (`ADMIN`, `OPERATOR`) are distinguished only by `isBuiltIn = true` — filter on that flag, not by name, when enforcing "built-in roles can't be deleted" (ticket 02, done). **But** the ADMIN-grant/revoke lock in ticket 03 is a *different, narrower* rule: it must key off `role.name === "ADMIN"` specifically, since OPERATOR is also `isBuiltIn: true` but is not the locked, highest-privilege role.
- `findRolesByUserId` returns plain `string[]` (not a `"ADMIN" | "OPERATOR"` literal union) as of ticket 01 — the ADMIN lock in ticket 03 should compare against the string `"ADMIN"` directly rather than relying on any type-level exhaustiveness.
- The e2e Playwright suite (`apps/e2e`) needs the full docker-compose stack to run live — worth a live run once the admin pages exist.
- `drizzle-kit generate` hangs on an interactive TTY prompt in this environment for enum-drop/column-rename-shaped diffs — ticket 01's migration was hand-written and validated with `drizzle-kit check` instead; do the same for any future migration that drops/renames rather than purely adds. Ticket 02 needed no migration at all (schema from ticket 01 already covered it); ticket 03 likely doesn't either, unless it needs new indices for the name/email search.
- Migration file for ticket 01 is `apps/api/drizzle/0005_wooden_black_cat.sql`; the next migration (if ticket 03 needs one) should be `0006_...`.
- **Shared-types package must be rebuilt after editing `packages/shared-types/src/index.ts`**: run `npm run build` in `packages/shared-types` — `apps/api` (and presumably `apps/web`) resolve it via `dist/`, not `src/`, so a source-only edit produces stale-looking "no exported member" errors in consumers until rebuilt.
- Boolean query/body flags need an explicit `@Transform(({ value }) => value === true || value === "true")` in the DTO — `@Type(() => Boolean)` alone coerces any non-empty string (including `"false"`) to `true`. See `apps/api/src/apps/roles/dto/delete-role-query.dto.ts`.

Ticket 03 will hit the same issue for `/users` — either get a Docker-based generation run working or hand-write the new `apps/web/lib/api-client/*.ts` request helpers against the documented shapes rather than relying on generated types.
