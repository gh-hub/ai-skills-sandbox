# ADR-001: Roles enum-to-table migration

## Status

Accepted (2026-08-01)

## Context

The prior roles/permissions plan (`plans/done/20260731_194131-user-roles-permissions/`, see its ADR-001) introduced `role` as a Postgres `pgEnum` (`ADMIN`, `OPERATOR`) directly on the `user_roles` join table, on the explicit assumption that the role set was fixed and small. This plan breaks that assumption: ADMINs must be able to create arbitrary new roles at runtime, and a Postgres enum's value set cannot be extended without a schema migration for every new value — it cannot represent admin-created data.

This is the first migration in this codebase that changes the *type* of an existing, populated column rather than purely adding new tables/columns. The prior migration (introducing `user_roles` itself) was purely additive; this one is not.

## Decision

**New `roles` table**: `id` (uuid PK), `name` (text, unique), `is_built_in` (boolean, not null). A migration seeds two rows, `ADMIN` and `OPERATOR`, both with `is_built_in = true`.

**`user_roles` column swap**: the existing `role` enum column is replaced with `role_id` (uuid, FK → `roles.id`, not null). The `user_id` FK keeps its existing `onDelete: "cascade"` behavior; `role_id` gets an FK behavior consistent with the pattern already used elsewhere in this schema for FK columns. The existing unique constraint on `(user_id, role)` moves to `(user_id, role_id)`.

**Backfill is required, not optional**: existing `user_roles` rows currently hold the string values `'ADMIN'`/`'OPERATOR'` in the enum column. The migration must backfill each existing row's new `role_id` to point at the corresponding newly-seeded `roles` row's id, in the same migration that seeds those rows (ordering matters: seed first, then backfill, then drop the old column and enum type). This is materially more involved than the codebase's prior migrations, which only added new tables/columns against an empty or unaffected data set.

**JWT/guard contract is explicitly unaffected**: `SessionTokenPayload.roles`, `AuthUser.roles`, and `MeResponse.roles` remain `roles: string[]` of role *names*. The existing `RolesGuard` + `@Roles('ADMIN','OPERATOR')` decorator pattern (`apps/api/src/apps/auth/roles.guard.ts`, `roles.decorator.ts`), and its use on `AwardsController`, needs zero code changes — it already matches by name string, never by the enum type or any id. Only how `user_roles` is stored and joined changes; nothing about how roles are read out of a user's session changes.

## Consequences

- This migration touches live data (existing `user_roles` rows), unlike every prior migration in this codebase, which only added structure. It should be reviewed and tested with particular care around migration ordering (seed → backfill → drop old column/enum) and should not be treated as a routine additive change at tickets/implement time.
- The old Postgres enum type itself must eventually be dropped once the column referencing it is gone — leaving it in place would be a stray, confusing artifact for later readers.
- Nothing downstream of `request.user.roles` (route guards, frontend role-based rendering, JWT issuance/verification) needs to change — the migration's blast radius is fully contained to the `roles`/`user_roles` tables and whatever repository code reads/writes `user_roles.role_id` instead of `user_roles.role`.
- Because `roles.name` is now data rather than a type, nothing at the database level prevents someone from creating a role literally named `ADMIN` or `OPERATOR` a second time if the application layer doesn't enforce uniqueness beyond the column's `unique` constraint — the unique constraint on `name` is the only backstop, and application-level validation/tickets should account for the built-in names already occupying `ADMIN`/`OPERATOR`.
