# ADR-001: Roles data model, JWT claim, and guard pattern

## Status

Accepted (2026-07-31)

## Context

The app currently has no concept of user privilege — every logged-in user can perform the same actions, and the `awards` PATCH/DELETE routes have no guard at all. We need to introduce a small, fixed set of roles (`ADMIN`, `OPERATOR`) that can be attached to a user, checked cheaply on both the backend (to guard mutation routes) and the frontend (to conditionally render UI), without adding a database round trip to every authenticated request.

This is the first place the codebase needs: (a) a Postgres enum type, (b) a claim in the session JWT beyond basic identity, and (c) any guard beyond the existing binary "logged in or not" (`RequireAuthGuard`). Whatever is chosen here becomes the template other role-gated features in this codebase will follow.

## Decision

**Data model**: a single `user_roles` join table (`user_id` FK → `users.id`, `role` typed as a new `pgEnum` with values `ADMIN`/`OPERATOR`), with a unique constraint on `(user_id, role)`. No separate `roles` lookup table — the role set is fixed and small, so a two-table design (as used for `awards`/`like_awards`, where the second entity is genuinely user-managed data) would be over-engineering here. The uniqueness constraint on the pair is what allows multiple roles per user while preventing duplicate role rows.

**JWT contract**: `SessionTokenPayload` (built in `auth.service.ts`'s `buildSession()`) gains `roles: string[]`, populated from `user_roles` at login/session-build time. `verifySessionToken()` passes the claim through unchanged. The shared `AuthUser` type (`packages/shared-types/src/index.ts`), and therefore `GET /auth/me`'s response, is extended the same way. A JWT with no `roles` claim (issued before this change) is treated as `roles: []` — not an error, and not a forced logout. Roles are only refreshed on next login, since they're baked into the token at issuance; this is accepted as a bounded staleness window (matching the token's own expiry) rather than something requiring live re-checks.

**Guard pattern**: a new `@Roles(...)` route decorator plus a `RolesGuard`, applied per-route via `@UseGuards(RolesGuard)` — matching the existing `RequireAuthGuard` convention rather than becoming a new global `APP_GUARD`. `RolesGuard` composes with authentication: absent `request.user` → 401; authenticated but missing the required role → 403. It replaces the bare `RequireAuthGuard` on `POST /awards` and newly guards `PATCH /awards/:id` and `DELETE /awards/:id` (previously fully open).

## Consequences

- Adding a role check to any future route is a two-line change (`@UseGuards(RolesGuard)` + `@Roles(...)`), consistent with how `RequireAuthGuard` is already used — no new architectural pattern needs to be learned for the next role-gated route.
- Because roles live in the JWT, the backend never queries `user_roles` on a per-request basis for authorization checks — cheap, but means a role granted/revoked mid-session doesn't take effect until the user's token is reissued (next login, or natural 7-day expiry). This is an explicit tradeoff, not an oversight — flagged in the grill decisions as "no forced session invalidation."
- The frontend gets roles for free via the existing `useMe()` call (no new endpoint), since `AuthUser`/`MeResponse` already flows through that hook.
- Introducing a real Postgres enum (`pgEnum`) is new to this codebase (previously unused, though available via drizzle-orm) — this migration becomes the reference example for any future enum-typed column, the same way migration 0003 (`like_awards`) is the reference for join tables.
- Because role assignment has no API surface (out of scope — direct DB writes only), there is no audit trail or application-level validation of who assigns roles to whom. If that becomes a requirement later, it will need its own design (endpoint, authorization-of-the-authorizer, audit log) — not covered by this ADR.
- The unique `(user_id, role)` constraint means "grant a role a user already has" is a safe no-op at the DB level if ever scripted, rather than producing duplicate rows.
