- **Deviation from the ticket's literal wording**: the ticket said to move `isStackAlreadyRunning()` into `global-setup.ts`. This sandbox unexpectedly had Docker available this session (`docker info` worked after `open -a Docker` + a short wait), so I ran the actual suite instead of relying on static checks alone — and this caught a real bug the spec didn't anticipate: Playwright's task runner (confirmed by reading `playwright@1.61.1`'s bundled `lib/runner/index.js`) runs the `webServer` plugin's setup (which invokes `docker compose up --build`) *before* the `globalSetup` task. If the probe lived in `global-setup.ts`, by the time it ran the stack it's checking for would already have been started by this very invocation's `webServer`, so `wasAlreadyRunning` would always be `true` — permanently breaking the cold-stack teardown case. I reproduced this exact failure in a real run (stack stayed up after a cold-stack suite completed), then fixed the design: the probe stays in `playwright.config.ts` (the only point guaranteed to execute before `webServer` starts anything — config module evaluation), computed once into `export const wasAlreadyRunning`, which `global-setup.ts` imports directly and closes over in its returned teardown function. This still satisfies the underlying intent of item 10 (no `process.env` round-trip, no separate `global-teardown.ts` process/file, single source of truth) — just not the literal "lives in global-setup.ts" instruction. The globalSetup-returns-teardown-function mechanism itself (the other assumption flagged in spec.md's Further Notes) was separately confirmed correct by reading the same runner file — no fallback needed for that part.
