# Implement notes — 03 Users API

## What was built

`UsersModule` (`apps/api/src/apps/users/`) gains a full controller/service, following the `RolesModule`/`AwardsModule` structure:

- `users.controller.ts` (`UsersController`): `GET /users`, `POST /users/:userId/roles`, `DELETE /users/:userId/roles/:roleId`. Every route individually carries `@UseGuards(RolesGuard) @Roles("ADMIN")` (per-method, matching `RolesController`/`AwardsController` precedent) — no ungated route.
- `users.service.ts` (`UsersService`): injects both `UsersRepository` and `RolesRepository` (imported via `RolesModule`, which `RolesModule` already exports per ticket 02).
  - `getPage({page, limit, search})` — mirrors `LikesService.getPage` exactly: count + page query, then a second batched query for roles across all page user ids (`findRolesForUserIds`), grouped via a new `users-roles.util.ts#groupRolesByUserId` (same shape as `likes-awards.util.ts#groupAwardsByLikeId`).
  - `grantRole(userId, roleId)` / `revokeRole(userId, roleId)` — both follow the same guard-clause order: resolve user (404) → resolve role (404) → `assertNotAdminRole` (400, checks `role.name === "ADMIN"`) → the operation-specific check (409-already-held via `findAssignment` before insert for grant; 404-not-held via a `delete().returning()` empty-result check for revoke, mirroring `AwardsRepository.deleteAward`'s existing not-found convention).
- `users.repository.ts` — added to the existing file (did not touch `findRolesByUserId`, already correct from ticket 01): `countMatching(search)`, `findPage(limit, offset, search)`, `findRolesForUserIds(userIds)`, `findAssignment(userId, roleId)`, `insertAssignment(userId, roleId)`, `deleteAssignment(userId, roleId)`. Search filter is a private `searchFilter(search)` helper building `or(ilike(users.name, pattern), ilike(users.email, pattern))`, returning `undefined` (no WHERE clause) when `search` is falsy — drizzle accepts `where(undefined)` as "no filter", same as the untouched `hasStoryFilter`-style precedent in `likes.repository.ts`.
- `users.module.ts`: now imports `RolesModule` (for `RolesRepository`) alongside `DbModule`; registers `UsersController`; still exports `UsersRepository` (unchanged, `AuthModule` depends on it).
- `apps/api/src/app.module.ts`: added `UsersModule` to the top-level imports array for explicitness — it was already transitively reachable via `AuthModule`'s existing `UsersModule` import (so this wasn't strictly required for the routes to register), but every other controller-bearing module is listed explicitly there, so this matches that convention.
- `packages/shared-types/src/index.ts`: added `UserRoleSummary` ({id, name} — deliberately narrower than `Role`, per ticket 02's gotcha note), `UserListItem` ({id, name, email, roles: UserRoleSummary[]}), `UsersPage` ({items, total, page, limit, totalPages}), `GrantUserRoleRequest` ({roleId}). Rebuilt `dist/` (`pnpm run build`) so `apps/api`'s typecheck picks them up.
- `apps/api/src/apps/users/dto/`: `get-users-query.dto.ts` (`GetUsersQueryDto` — identical page/limit shape to `GetLikesQueryDto`, plus optional `search: string`), `user-role.dto.ts`, `user-list-item.dto.ts`, `users-page.dto.ts` (swagger DTOs implementing the shared types above), `grant-role.dto.ts` (`GrantRoleDto` — `roleId` validated with `@IsUUID()`).
- `apps/api/src/apps/users/users.spec.ts` — new full-HTTP integration suite (real `INestApplication`, testcontainers Postgres, real migrations, supertest — same shape as `roles.spec.ts`/`awards.spec.ts`), 23 tests covering: 401/403/200 (envelope shape, inline roles) on `GET /users`; pagination (default page/limit, explicit page 2, `total`/`totalPages` computed from a 15-user seeded batch matched via a unique `search` term to keep counts deterministic across the whole suite's shared DB); limit capped at 100 (over-limit request rejected with 400 by class-validator's `@Max`, not silently clamped); case-insensitive partial search by both name and email; 401/403/204/400(ADMIN target)/409(already-held)/404(missing user)/404(missing role) on `POST /users/:userId/roles`; 401/403/204/400(ADMIN, own row)/400(ADMIN, other user)/404(missing user)/404(missing role)/404(not held) on `DELETE /users/:userId/roles/:roleId`.

## Key decisions / assumptions

- **Pagination test isolation**: since `users.spec.ts` shares one Postgres container across all tests in the file (like every other integration spec here) and `GET /users` has no filter besides `search`, the pagination test seeds 15 users under a single unique-per-run name prefix and always searches by that prefix, so `total`/`totalPages` are deterministic regardless of how many other users earlier tests in the file created. This is the same technique `roles.spec.ts`/`awards.spec.ts` use with `uniqueRoleName`/`uniqueTitle` for isolating an individual assertion, just applied to a count instead of an existence check.
- **`limit=101` behavior**: the ticket says "maximum limit is 100" without specifying whether an over-limit request is clamped or rejected. This spec's `GetUsersQueryDto` reuses `GetLikesQueryDto`'s exact validation (`@Max(MAX_LIMIT)`), which **rejects** with 400 rather than clamping — matching the established `GET /likes` behavior byte-for-byte (verified: `GetLikesQueryDto` has no custom exception filter overriding class-validator's default 400). Flagging here since the ticket file only said "capped at 100" without saying which behavior "capped" means.
- **Grant/revoke check order**: both handlers resolve the target user first (404), then the role (404), then apply the ADMIN-lock check (400), then the operation-specific check (409 for grant-already-held, 404 for revoke-not-held). This order isn't specifically tested by any single request that trips two failure conditions at once (each test scenario only ever has exactly one bad input), so the ordering itself isn't a hard contract — chosen to mirror `RolesService.remove`'s existing guard-clause chain (resolve entity → business-rule check → in-use check).
- **ADMIN lock is enforced purely by role name**, not by checking "is this the ADMIN user" some other way — `assertNotAdminRole` checks `role.name === "ADMIN"` on the *role being granted/revoked*, independent of who's calling or which user is targeted. This directly satisfies user stories 28/29/30 (rejected regardless of caller or target, including the admin's own row) since the check never inspects the caller or target user at all, only the role.
- **`insertAssignment` relies on `findAssignment` for the 409 check** rather than catching a unique-constraint violation from the DB (the `(user_id, role_id)` unique index from ticket 01 would also reject a duplicate insert) — chosen because catching a specific Postgres error code to translate into a `ConflictException` is more fragile/opaque than a pre-check `SELECT`, and this codebase's existing precedent (`RolesService.create`'s `findByName`-before-insert) already established the pre-check pattern for the equivalent duplicate-name case.
- **No new unit-test files for `users.service.ts` or the new `users.repository.ts` methods** — mirrors ticket 02's precedent exactly (`RolesService`/`RolesRepository` also have zero dedicated unit-test files; `roles.spec.ts`'s full-HTTP integration suite is the only test coverage for the whole `RolesModule` request/response/business-rule surface). Kept `users.repository.spec.ts` (the existing mocked-chain unit test for `findRolesByUserId`, from ticket 01) completely untouched — did not add mocked-chain tests for the six new repository methods added this ticket, consistent with that same precedent.

## Gotchas / things ticket 04 (admin roles page) and ticket 05 (admin users page) should know

- **`GET /users` response shape**: `{items: [{id, name, email, roles: [{id, name}]}], total, page, limit, totalPages}`. Each item's `roles` array includes **every** role the user holds, including `ADMIN` if applicable — the frontend (ticket 05) is responsible for rendering `ADMIN` as a non-interactive badge and excluding it from the toggle checkboxes (per spec user stories 17/18); the API does not filter it out or mark it specially in any way (no `isAdmin`/`isLocked` flag on the per-role object — just `{id, name}`, same shape for every role).
- **Query params**: `page` (default 1), `limit` (default 10, **rejects** >100 with 400 rather than clamping — matches `GET /likes` exactly), `search` (optional, matches name OR email, case-insensitive, partial). All three are plain query-string params, not part of a request body.
- **Grant**: `POST /users/:userId/roles` with JSON body `{roleId}` (must be a valid UUID format or 400s at the DTO validation layer, before the service layer's own 404-if-not-found check ever runs). 204 on success, no response body (matches the spec's stated open-question resolution: no updated-role-set-inline response; frontend must re-fetch).
- **Revoke**: `DELETE /users/:userId/roles/:roleId` — both `userId` and `roleId` are path params (both `ParseUUIDPipe`-validated, so a non-UUID-shaped id 400s before reaching the service).
- **ADMIN lock**: attempting to grant or revoke the `ADMIN` role via either endpoint always 400s, for any user, including the calling admin's own row. There is no way to distinguish "this would have been fine but you're not allowed to touch ADMIN" from "some other 400" in the response body (`BadRequestException` with a plain string message) — if ticket 04/05's frontend wants to special-case this in the UI (e.g., a specific toast message), it should key off the fact that `ADMIN` is simply never rendered as a togglable checkbox at all (per spec), so the 400 path should be unreachable from the intended UI and doesn't need bespoke handling.
- **Custom role visibility**: a role created via `POST /roles` immediately shows up in every subsequent `GET /users` call's per-user `roles` array (if assigned) and is immediately grantable via `POST /users/:userId/roles` — there's no caching/staleness concern between `RolesModule` and `UsersModule`, they both read live from the same `roles`/`user_roles` tables.
- `UsersModule` now imports `RolesModule` (for `RolesRepository` injection into `UsersService`) — if ticket 04/05 add any other backend module that needs both repositories, importing `RolesModule` directly (as done here) is the established way to get `RolesRepository`, rather than reaching into `UsersModule`.
