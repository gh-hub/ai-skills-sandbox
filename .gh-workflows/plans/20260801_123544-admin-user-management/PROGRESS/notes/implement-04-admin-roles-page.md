# Implement notes — 04 Admin roles page (`/admin/roles`)

## What was built

Frontend-only ticket, consuming the already-built `RolesModule` API (ticket 02):

- `apps/web/app/admin/roles/page.tsx` — new route. Renders `null` while `useMe()` is loading, `null` for anonymous visitors, `null` for logged-in non-admins (checked via a new `isAdmin(user)` helper) — no login-prompt branch at all, per spec (unlike `create-award-section.tsx`'s anon → prompt / non-privileged → null pattern). Otherwise renders a heading, a back link to `/admin`, the roles list, and the create-role form.
- `apps/web/components/roles-list.tsx` (`RolesList`, `RolesListSkeleton`) — fetches via `useRoles()`, renders each role as an `<li>` with its name, a "Built-in" pill badge (same visual convention as the header's role badges / `award-badge.tsx`) for `ADMIN`/`OPERATOR`, and a delete icon button (only rendered — not disabled — for non-built-in roles). Manages `deletingRole` state and renders `DeleteRoleModal`.
- `apps/web/components/create-role-form.tsx` — name-only form (zod + react-hook-form, same shape as `create-award-form.tsx`), calls `useCreateRole()`, surfaces the 409 duplicate-name server message via the same `extractServerErrorMessage` pattern already used in `auth-modal.tsx`.
- `apps/web/components/delete-role-modal.tsx` (`DeleteRoleModal`) — one Dialog, two steps, driven by whether the delete attempt errored with a `RoleInUseError`: step 1 asks for a plain confirm and calls `DELETE /roles/:id` (no `force`); on a 409 it switches in place to show the affected users' name/email and a "Delete anyway" button that retries with `force=true`. Mirrors `edit-award-modal.tsx`'s two-step-dialog structure, but the step transition is error-driven here rather than form-submission-driven.
- `apps/web/lib/api-client/roles.ts` (new) — `useRoles()`, `useCreateRole()`, `useDeleteRole()`. `useDeleteRole`'s `onSuccess` invalidates both `rolesQueryKey` and `usersListQueryKeyPrefix` (see below). Exports a `RoleInUseError` class (thrown from the mutation's `mutationFn` when the DELETE response is 409 with an `affectedUsers` array) so the modal component can `instanceof`-check it instead of re-parsing the response body itself.
- `apps/web/lib/api-client/users.ts` (new, minimal) — exports only `usersListQueryKeyPrefix = ["users", "list"] as const`. This exists purely so `useDeleteRole`'s cache invalidation has something stable to invalidate ahead of ticket 05 actually building the users list query. **Ticket 05 must nest its real query key under this exact prefix** (e.g. `[...usersListQueryKeyPrefix, page, search]`) — React Query's `invalidateQueries` matches by key prefix, so anything ticket 05 builds under this array will get invalidated correctly by this ticket's role-deletion flow without ticket 05 needing to change anything here.
- `apps/web/lib/api-client/auth.ts` — added `isAdmin(user)`, same shape/pattern as the existing `canManageAwards(user)`. Ticket 05 (users page gating) and ticket 06 (header link + `/admin` hub gating) should reuse this directly rather than re-deriving it.

## Gotchas for ticket 05 (and anyone else touching this API surface)

- **`apps/api/openapi.json` and `apps/web/lib/api-client/schema.d.ts` were stale** going into this ticket — both predated tickets 02/03's `RolesModule`/`UsersModule`, so `/roles` and `/users` weren't in the generated frontend types at all. Regenerated both (`pnpm run generate:openapi` in `apps/api`, then `pnpm run generate:api-types` in `apps/web`) — this is now current and should be kept in sync (regenerate again) whenever a backend route changes, same as any other ticket touching the API surface.
  - Regenerating required first deleting a stale `apps/api/tsconfig.build.tsbuildinfo` — `nest build` was silently producing an **empty** `dist/` (exit 0, no error) because its incremental-build cache believed a from-before-ticket-01 build was already up to date. This is exactly the class of issue `coding-rules/node-typescript-docker.md` already documents for Docker build contexts, just hit locally here. If a future ticket's `nest build` produces no `dist/` output with no error, check for this first.
- **openapi-fetch types `error` as `never` for any route whose non-2xx responses aren't documented with an explicit `@ApiResponse`-family decorator** (neither `RolesController`'s 409s nor `POST /roles`'s 409 have one). `roles.ts`'s `useDeleteRole` works around this by casting `result.error as unknown` before inspecting it. If ticket 05 needs to inspect a non-declared error body (e.g. `UsersController`'s 400/404/409s), the same cast-to-`unknown` pattern will be needed — see `apps/web/lib/api-client/roles.ts`.
- **`usersListQueryKeyPrefix`** (see above) — reuse it, don't invent a separate key, or role-deletion's invalidation silently stops reaching the users page's cache.
