# ADR-002: `GET /users` is the codebase's first paginated/searchable list endpoint

## Status

Accepted (2026-08-01)

## Context

Every existing list endpoint in this codebase (e.g. `GET /awards`) returns a simple, full, unpaginated list. `GET /users` is being introduced as part of this plan to back `/admin/users`. A user table is expected to grow in a way that award lists have not needed to account for, and an ADMIN browsing users needs to be able to find a specific person by name or email rather than scanning a full dump.

## Decision

`GET /users` supports pagination and search from the start, as a deliberate choice — not deferred the way it would be for a typical new list endpoint in this codebase. Search is a single query parameter matched case-insensitively, as a partial match, against both name and email.

This is a conscious deviation from the codebase's existing simple-list convention, made because building pagination/search in from the start avoids a later breaking change to the endpoint's response shape once a real user base exists — retrofitting pagination onto a shipped, consumed "plain array" response is a breaking change for any client already depending on that shape, whereas this endpoint has no such client yet.

The exact response shape (e.g. `{ items, total, page, limit }` or equivalent) and the default page size are explicitly **not** decided here — they are implementation-level details left to the spec/tickets phase.

## Consequences

- `GET /users` will not return a bare array like `GET /awards` does — any frontend code consuming it must unwrap whatever paginated envelope spec/tickets defines, and must not assume it can reuse the same simple-list fetch pattern used for awards.
- This becomes the reference example for any future list endpoint in this codebase that anticipates similar growth — the same way the prior roles/permissions plan's guard pattern became the reference for role-gated routes.
- Because the shape isn't pinned down yet, spec/tickets must decide it before implementation starts on the users list endpoint or its frontend consumer — this ADR intentionally leaves that decision open rather than presupposing it.
