# ADR-001: Awards schema and API shape

## Status
Accepted (grill phase output — implementation to follow in spec/tickets)

## Context
The existing "thanks" feature is implemented as the `likes` table and the
`apps/api/src/apps/likes/` module (module/controller/service/repository/dto/tests
split, established in commit 078aec5 as this repo's reference architecture for a
feature module). We're adding "awards" — a badge/recognition concept that a thanks
submission (`likes` row) can optionally carry one or more of. This decision records
the schema and API shape so the team doesn't have to re-derive it in six months.

## Decision

### New `awards` table
Mirrors the shape and conventions of the existing `likes` table:
```ts
export const awards = pgTable("awards", {
  id: uuid("id").primaryKey().defaultRandom(),
  createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
  title: text("title").notNull(),
  description: text("description").notNull(),
  icon: text("icon"), // optional; UI supplies a default fallback icon when absent
});
```

### New many-to-many join table
A join table (working name `like_awards`, to be finalized at spec/implementation
time to best fit existing naming) links `likes` and `awards`:
```ts
export const likeAwards = pgTable("like_awards", {
  id: uuid("id").primaryKey().defaultRandom(),
  likeId: uuid("like_id").notNull().references(() => likes.id, { onDelete: "cascade" }),
  awardId: uuid("award_id").notNull().references(() => awards.id, { onDelete: "cascade" }),
});
```
- `likeId → likes.id` cascades on delete: deleting a thanks story removes its join
  rows (standard cleanup of a dependent row, not the primary resource).
- `awardId → awards.id` cascades on delete: deleting an award removes its join rows
  from any thanks story it was attached to, but leaves the `likes` row itself
  untouched. This is a deliberate choice, not a default: confirm/implement this
  `onDelete` behavior explicitly rather than assuming it matches
  `likes.userId → users.id`, which is documented as **not** cascading today — the
  two FKs on this table have different cascade behavior on purpose and should not
  be copy-pasted from each other.
- A `likes` row may have zero, one, or many rows in this join table; an `awards` row
  may likewise be referenced by zero, one, or many join rows (used to compute the
  "times given" count shown on `/awards`).

### Full REST module mirroring `likes`
`apps/api/src/apps/awards/` follows the same structural convention as
`apps/api/src/apps/likes/`:
- `awards.module.ts`, `awards.controller.ts` (`@Controller("awards")`),
  `awards.service.ts` (thin orchestration), `awards.repository.ts` (all Drizzle
  query logic, `@Inject(DATABASE_CONNECTION)`), `dto/` (class-validator +
  class-transformer + `@nestjs/swagger` `@ApiProperty`/`@ApiPropertyOptional`).
- One test file per layer, following the `likes` precedent
  (`likes.spec.ts` Testcontainers integration, `likes.service.spec.ts`,
  `likes.repository.spec.ts` mocked unit tests) — expect
  `awards.spec.ts` / `awards.service.spec.ts` / `awards.repository.spec.ts`.
- Full CRUD surface is implemented even though the frontend only consumes list and
  create for now: `GET /awards`, `GET /awards/:id`, `POST /awards`,
  `PATCH /awards/:id`, `DELETE /awards/:id`.
- Response shapes and conventions follow existing patterns: plain DTO classes
  returned directly (no envelope), pagination shape `{ items, total, page, limit,
  totalPages }` if/when `GET /awards` is paginated (TBD at spec time — 7+ awards may
  not need pagination initially), Swagger `@ApiProperty` on every DTO field.

### Auth split
- `POST /awards` requires a logged-in user. No admin/role concept exists anywhere in
  this codebase (confirmed absent in `apps/api/src/apps/auth/`) and none is being
  introduced — this is purely an "authenticated vs. anonymous" check.
- `GET /awards`, `GET /awards/:id`, `PATCH /awards/:id`, and `DELETE /awards/:id`
  remain open, unauthenticated, matching how the existing `likes` endpoints work
  today.
- The existing `@CurrentUser()` decorator is used optionally on `POST /likes`
  today, but there is currently no mandatory-auth guard used anywhere in the
  codebase. `POST /awards` is likely the **first** endpoint that needs one — before
  implementing, check `apps/api/src/apps/auth/` for any existing guard to reuse; only
  build a new guard if nothing suitable exists.

### Cascade-delete behavior (summary)
Deleting an award is a hard delete with join-table cleanup: the award row and any
`like_awards` rows referencing it are removed; the `likes` (thanks) rows that
referenced it are left fully intact, simply losing that one badge.

## Consequences
- The `awards` and `like_awards` tables, plus the module skeleton, become the
  long-term shape for any future award-related work (e.g. if edit/delete UI or
  award analytics are added later, they build on this same schema).
- Because `POST /awards` introduces the first mandatory-auth guard in the codebase,
  whatever guard mechanism is chosen here becomes a precedent for future
  login-required endpoints — worth getting right/consistent rather than
  ad hoc.
- Seed data for the 7 initial awards ships as a Drizzle migration (numbered SQL
  file alongside `0000_*`/`0001_*`/`0002_*` in `apps/api/drizzle/`), so schema
  history and initial data are versioned together.

## Alternatives considered
- Storing awards as a fixed enum/array on the `likes` row instead of a separate
  table + join table — rejected because awards need independent lifecycle
  (create/update/delete, a description, a give-count) that a plain enum can't
  support, and new awards must be user-creatable.
- A single nullable `awardId` foreign key directly on `likes` — rejected because it
  can't represent more than one award per thanks story, which was an explicit
  requirement.
