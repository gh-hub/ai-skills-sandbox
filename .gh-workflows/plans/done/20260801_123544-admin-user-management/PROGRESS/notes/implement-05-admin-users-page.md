## What was verified (by reading code, not running anything live)

- `apps/web/app/admin/users/page.tsx` — route gating matches ticket 04's `/admin/roles` pattern exactly: renders `null` while `useMe()` is loading or `me.data === undefined`, `null` for non-admins via the shared `isAdmin(user)` helper (`apps/web/lib/api-client/auth.ts`), no login-prompt branch. Back link points to `/admin` (currently 404 — `/admin` hub is ticket 06, not this ticket; this is expected, not a bug).
- `apps/web/components/users-list.tsx` — debounced search (300ms `setTimeout`, reset on unmount/change), resets `page` to 1 whenever `search` changes, renders the existing `apps/web/components/pagination.tsx` component driven by the response's `page`/`totalPages`. `assignableRoles` is derived by filtering `ADMIN` out of `useRoles()`'s result set entirely, so the ADMIN role structurally cannot render as a checkbox anywhere on the page, including the logged-in admin's own row — this satisfies the "never a checkbox, even for the admin's own row" criterion by construction rather than by a per-row special case, which is a stronger guarantee than a naive implementation might give.
- ADMIN badge itself (`users-list.tsx`, `holdsAdmin` check) renders as a plain `<span>` pill, never an `<input>` — confirmed non-interactive.
- `apps/web/components/user-role-toggle.tsx` — one checkbox per assignable role per user; `isGranted` is derived purely from the user-list query response (not local state), so a grant/revoke's invalidate-and-refetch is the only thing that ever changes what's checked (no manual list patching, matching the spec's explicit requirement).
- `apps/web/lib/api-client/users.ts` — `useGrantUserRole` → `POST /users/{userId}/roles` with `{roleId}` body; `useRevokeUserRole` → `DELETE /users/{userId}/roles/{roleId}`; both call `queryClient.invalidateQueries({ queryKey: usersListQueryKeyPrefix })` on success, where `usersListQueryKeyPrefix = ["users","list"]` and `useUsers`'s real query key (`usersListQueryKey(page, search)`) nests under it (`[...usersListQueryKeyPrefix, page, search]`) — confirmed this is the same prefix ticket 04's `useDeleteRole` already invalidates, so both role-deletion (ticket 04) and grant/revoke (this ticket) correctly invalidate every cached page/search variant.
- **Shared roles cache key, traced explicitly (this was called out as a common integration bug to check)**: `apps/web/components/users-list.tsx` calls `useRoles()` from `apps/web/lib/api-client/roles.ts`, the exact same hook/query-key (`rolesQueryKey = ["roles","list"]`) that ticket 04's `apps/web/components/roles-list.tsx` uses. `useCreateRole`'s `onSuccess` invalidates `rolesQueryKey`. Since both pages' `useRoles()` calls share that one query key, creating a role on `/admin/roles` invalidates the cache entry this page's `useRoles()` is also subscribed to — no extra plumbing was needed or added, and none should be. This was verified by reading both files side by side, not assumed from the notes.
- **Mechanism behind "no reload needed"**: `apps/web/app/providers.tsx` constructs `new QueryClient()` with no config overrides, so React Query's default `refetchOnWindowFocus: true` is in effect. This is what makes a role created in another tab/window show up on this page without an explicit reload or a bespoke subscription — confirmed by reading `providers.tsx`, not inferred.
- Type-checked the frontend hook call shapes (`useUsers`'s query params, `useGrantUserRole`'s body) against `apps/web/lib/api-client/schema.d.ts`'s `UsersController_getPage`/`GrantRoleDto`/`UserListItemDto`/`UserRoleDto` — all consistent; `apps/api/openapi.json`/`schema.d.ts` did not need regeneration (ticket 03/04 already brought both current).
- Read `apps/e2e/tests/admin-users-page.spec.ts` (218 lines, 8 tests) in full: anonymous/non-admin/OPERATOR-all-render-nothing, ADMIN badge + never-a-checkbox (unscoped to any row), search by name and by email, pagination across a 15-user seed, grant-then-revoke toggle round-trip, a cross-tab "role created elsewhere, checkbox appears on refocus" test (explicitly exercises the `refetchOnWindowFocus` mechanism above), and the back-link href. The spec's assertions line up with what the implementation actually does. **Not executed.**
