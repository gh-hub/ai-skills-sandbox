Same gating pattern as tickets 04/05's `/admin/roles`/`/admin/users`: renders `null` while `useMe()` is loading, `null` for anonymous visitors, `null` for logged-in non-admins via the shared `isAdmin(user)` helper (`apps/web/lib/api-client/auth.ts`, already existed from ticket 04 — reused directly, not re-derived). ## Live e2e — ran, found and fixed 6 real bugs, ended 100% passing

Docker responded to `docker info` within a few seconds this session (no repeat of the flakiness that stalled two prior agent attempts on ticket 05). Brought up the e2e stack via Playwright's own `webServer` plugin (`docker compose up --build`, already configured in `playwright.config.ts` — no manual `docker compose` invocation needed) and ran the combined suite owed since ticket 04: `admin-navigation.spec.ts` + `admin-roles-page.spec.ts` + `admin-users-page.spec.ts` (27 tests), then the full suite (58 tests, all spec files). Final state: **58/58 passing**.

Getting there took four iterations, each surfacing a real, reproducible bug — not flakiness that went away on retry:

1. **My own spec's locator bug.** `admin-navigation.spec.ts`'s `getByRole("link", { name: "Roles" })` matched *both* hub cards. Playwright computes a link's accessible name from all its inner text, and the Users card's own description ("...grant or revoke their roles.") contains "roles" as a case-insensitive substring — so both `/admin/users` and `/admin/roles` links satisfied the query. **Fixed in the component**, not just the test: added explicit `aria-label="Users"` / `aria-label="Roles"` / `aria-label="Home"` to `apps/web/app/admin/page.tsx`'s three links, decoupling each link's accessible name from its (multi-paragraph) visible content. This is a real accessibility improvement, not a workaround.
2. **Email length limit, again.** `admin-users-page.spec.ts`'s `uniqueEmail()` combined a 12-char fixed prefix with a full 36-char UUID and this file's own long marker strings (e.g. `page-marker-<timestamp>-<index>`), pushing several generated emails' local parts past RFC 5321's 64-char cap — a real 400 from the backend's `@IsEmail()` DTO, not simulated. Same failure mode ticket 04 already hit and documented; fixed the same way (shortened base prefix, 8-char id instead of a full UUID).
3. **Session-cookie clobbering — this one was silently breaking 4 tests every time this file ran, never caught because it had never run live before.** `createUserViaApi` used `page.request.post("/api/auth/signup", ...)`. `page.request` shares `page`'s cookie jar, and a signup response sets a session cookie for the *new* user — so every call to this helper silently logged the test's ADMIN out and swapped in the new plain user's session. Every assertion after the first `createUserViaApi` call in the search, paging, toggle, and live-role-focus tests was then running against a 403'ing (non-admin) session, not the intended admin one. Fixed by switching to Playwright's isolated `request` fixture (a separate cookie jar), the exact precaution `admin-roles-page.spec.ts`'s in-use-role test already documents for the identical reason — just not one that had been applied here.
4. **Persisted-volume name collision.** `loginAsAdmin`'s default display name was a fixed literal ("Users Page Admin"). This e2e suite's Postgres volume persists across separate sessions (`global-setup.ts` only ever truncates the `likes` table), so every historical live run of this file added one more identically-named admin row. Once enough runs had accumulated (this session's second run tipped it over), a `li.filter({ hasText: admin.name })` locator became a strict-mode violation against every same-named row ever created, not just the current run's. Fixed by giving the default name a random 8-char suffix — same reasoning `uniqueEmail()` already exists for.
5. **Headless-Chromium focus-event limitation.** The cross-tab "role created elsewhere" test calls `page.bringToFront()` expecting it to fire the `visibilitychange` event React Query's `refetchOnWindowFocus` depends on (confirmed by reading `@tanstack/query-core`'s `focusManager.ts` directly — it's a `window.addEventListener("visibilitychange", ...)` listener, and `isFocused()` reads `document.visibilityState`). This didn't reliably fire across separate Playwright `Page` targets in headless Chromium — reproduced deterministically across two separate live runs, not a one-off flake. Fixed by explicitly dispatching `new Event("visibilitychange")` via `page.evaluate` right after `bringToFront()`, which exercises the app's real listener chain deterministically regardless of the harness's tab-activation semantics. Not an app bug: the underlying mechanism (`providers.tsx`'s unconfigured, default-`refetchOnWindowFocus: true` `QueryClient`) was already confirmed correct by reading code in ticket 05.
6. **A genuine regression in an unrelated, pre-existing spec.** `auth-flow.spec.ts`'s "a user granted ADMIN sees an ADMIN badge" test used an unscoped `page.getByText("ADMIN")` — Playwright's `getByText` does a case-insensitive substring match by default. This ticket's new header "Admin" link text now also satisfies that query for any ADMIN user, so the assertion became a strict-mode violation (2 matches: the link, and the actual role badge). This is a real, if narrow, blast-radius consequence of adding the header link — not test flakiness. Fixed by scoping the assertion to `page.getByRole("list", { name: "Roles" }).getByText("ADMIN")`, which is what the test was actually trying to check in the first place.

None of these were app-logic bugs in the admin feature itself (roles/users APIs, grant/revoke, deletion flows) — all fixes were in e2e test code, except item 1's `aria-label` additions, which are a small, defensible component improvement independent of testing.

## Notes for the review phase

- **Docker was not flaky this session** — `docker info` responded in a few seconds, and Playwright's own `webServer` plugin (`docker compose up --build`, pre-configured in `apps/e2e/playwright.config.ts`) handled bring-up/teardown automatically across five separate live runs in this one session with no hangs. The prior flakiness reported on tickets 01/02/04/05 may have been transient (or specific to those sessions' sandbox state) rather than a durable property of this environment — worth trying live e2e again early in future sessions rather than assuming it will stall.
- **The e2e Postgres volume persists across sessions** and is not reset except for the `likes` table (`apps/e2e/global-setup.ts`). By this session's runs, it held a substantial amount of accumulated historical test data (7+ pages of users at one point). This is what caused bug #4 above and is worth knowing about for future e2e work: any new test that scopes a locator by a fixed literal name/label (rather than a per-run-unique one) is at risk of an eventual strict-mode violation once enough live runs accumulate. Consider either (a) always using unique names/emails in new specs (the existing convention, just not consistently followed), or (b) extending `global-setup.ts` to truncate `users`/`user_roles`/`roles` too — out of scope for this ticket, flagging for whoever picks it up next (could be a `gh-debt-workflow` item).
