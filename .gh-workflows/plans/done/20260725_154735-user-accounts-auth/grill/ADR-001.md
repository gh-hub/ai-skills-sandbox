# ADR-001: Auth strategy: JWT in httpOnly cookie, bcrypt hashing, nullable user attribution on likes

## Status

Accepted (grill phase, 2026-07-25)

## Context

"Thanks, Claude" has no concept of users today — likes/stories are fully
anonymous, stored in a single `likes` table (`id`, `created_at`, `story`,
`hours_saved`). We're adding basic accounts so a logged-in visitor's
likes/stories can be attributed to them and shown with an avatar on the story
feed, while anonymous use keeps working unchanged. The API
(`apps/api`, NestJS + Drizzle + Postgres) currently has zero auth-related
dependencies installed (no bcrypt, no passport, no jsonwebtoken). This ADR
covers the decisions with lasting architectural consequences: the shape of
the new `users` table, how sessions are carried between frontend and API, how
passwords are hashed, and how likes reference users. It does not cover UI
placement or avatar styling — those are cosmetic and tracked as plain
decisions, not architecture.

## Decision

**`users` table (new module, new Drizzle table):**
- `id` — uuid, primary key, default random
- `name` — text, required
- `email` — text, unique, required
- `password_hash` — text, required
- `created_at` — timestamp with timezone, default now
- No other columns. No profile fields, no roles, nothing speculative.

**Session mechanism:** the API issues a JWT on successful login or signup,
set as an httpOnly, secure-in-production, sameSite cookie. The token is never
returned in a JSON response body and never touched by frontend JS (no
localStorage, no Authorization header). Because the cookie is httpOnly and
therefore unreadable from JS, the API must also expose a "who am I" endpoint
(e.g. `GET /auth/me`) that the frontend calls on load to restore login state
after a page reload. The JWT signing secret comes from an environment
variable, following the existing env-config pattern used for `DATABASE_URL`
(see `apps/api/src/db/db.module.ts` / `ConfigService` usage) rather than a new
ad hoc pattern.

**Password hashing:** bcrypt. New dependencies to add: bcrypt, a JWT library
(jsonwebtoken or `@nestjs/jwt`), and cookie-parsing middleware/support — none
of these exist in the API today.

**Likes attribution:** `likes.user_id` is a new **nullable** FK column
referencing `users.id`. A valid session at request time sets `user_id` to
that user's id; no session leaves it null. There is no uniqueness constraint
on `(user_id)` or `(user_id, ...)` — a user can like/share any number of
times, identical to today's unlimited anonymous behavior. This keeps
anonymous submission a first-class, unchanged path rather than a special case
bolted onto an auth-required flow.

## Consequences

- The `likes` table gains a nullable FK; existing rows are unaffected (all
  remain `user_id = null`, i.e. anonymous), so this is a backward-compatible
  migration.
- Three new runtime dependencies land in `apps/api` (bcrypt, a JWT library,
  cookie support) — first auth dependencies in the codebase, so this also
  sets the pattern future auth-adjacent work will follow.
- Because sessions are httpOnly-cookie-based rather than header/localStorage
  token-based, every relevant API endpoint (`/auth/me`, like/story creation)
  must read the cookie server-side; the frontend cannot inspect or manage the
  token itself, only trigger login/logout/me calls.
- The nullable, unconstrained `user_id` means attribution is purely
  best-effort based on session presence — there's no retroactive attribution,
  no merge of anonymous history into an account, and no enforcement that a
  user can only appear once per like. Revisiting any of that (e.g. one-like-
  per-user) would require a schema/constraint change, not just app logic.
- No password reset, email verification, rate limiting, OAuth, or profile
  editing is included — those remain explicitly out of scope and would each
  need their own decision if picked up later.

## Alternatives rejected

- JWT returned in the response body, stored in localStorage, sent via an
  Authorization header — rejected due to XSS exposure of the token and to
  keep token handling out of frontend JS entirely.
- argon2 for password hashing — rejected in favor of bcrypt as the simpler,
  more common choice for this codebase's scope.
- One-like-per-user with unlike/toggle semantics on `likes.user_id` —
  rejected as bigger scope than this "really basic" feature calls for.
