# ADR-001: Single global header + React Context for cross-route-tree scroll-state plumbing

## Status
Accepted

## Context

This application currently has two separate header components:
1. A static, always-visible bar in `layout.tsx` (Awards link + theme toggle), present on every route
2. A home-page-only sticky header (`sticky-header.tsx`), conditionally visible based on scroll position

The user explicitly requested consolidating these into a single unified header component that:
- Acts as the one source of truth for header content and behavior across all routes
- Is always mounted globally (in `layout.tsx`) and always `position: fixed`
- Shows different content based on route and scroll state

This consolidation creates a cross-tree state plumbing problem: the header is mounted in `layout.tsx` (an ancestor of all routes), but the scroll-trigger element (the home page's hero card) only exists inside `page.tsx` (a descendant route). A descendant needs to communicate scroll state upward to the header without prop-drilling through every route's component tree.

React Context (`createContext` / `useContext`) is the standard React mechanism for this scenario. No app-level Context currently exists in `apps/web` (Context usage is limited to shadcn/ui library internals), so this plan establishes the first such precedent.

## Decision

Introduce a new React Context (`HeroVisibilityContext`) that:
- Wraps both the unified header component and all route children in `layout.tsx`
- Carries a boolean indicating whether the home page's hero card has scrolled fully out of the viewport
- Is written to by the home page's scroll-detection hook (evolving the existing `useIsScrolledPast` pattern)
- Is read from by the unified header to determine whether to show `HeaderAuthControl`
- Defaults to "hero not visible" when not written to, so non-home routes automatically show login info

This approach avoids prop-drilling through every route's tree and produces a clean separation: scroll detection is a concern of the home page, while header visibility logic is a concern of the header component.

## Consequences

**Positive:**
- Produces a single unified header component as requested by the user
- Avoids prop-drilling that would couple the header to every route's structure
- React Context is a built-in React feature (no new dependencies)
- Establishes a reusable pattern for future cross-tree state in this codebase
- Non-home routes automatically get correct default behavior ("show login") without extra code
- The pattern is well-understood by React developers and commonly used for exactly this scenario

**Negative:**
- Introduces the first app-level Context in this codebase, adding to conceptual complexity
- Requires understanding how Context defaults work and when providers wrap components
- If scroll behavior is ever needed on other routes, Context logic would need refining (though current default is sufficient)
- Testing the header's visibility logic requires understanding Context plumbing (though Playwright e2e tests will exercise the behavior end-to-end)

## Alternatives considered

1. **Keep two components (layout.tsx bar + sticky-header.tsx) with a shared `HeaderControls` sub-component**
   - Avoids Context plumbing entirely
   - Provides markup reuse (Awards link + theme toggle shared)
   - Rejected because it doesn't produce "one component" — two still-separate elements with internal sharing is not what the user requested

2. **Global state management (Redux, Zustand, etc.)**
   - Provides centralized state for cross-tree communication
   - Adds a new external dependency and conceptual overhead
   - Overkill for a single boolean flag
   - Rejected in favor of React's built-in Context mechanism

3. **Prop-drilling hero visibility through every route**
   - Avoids Context entirely
   - Requires every route component to accept and pass through `heroIsVisible` props
   - Tightly couples the header concern (hero visibility) to every route's component tree
   - Creates maintenance burden if route structure changes
   - Rejected in favor of Context's cleaner separation of concerns

4. **Conditionally fixed header (normal flow on non-home, fixed only on home after scroll)**
   - Avoids the need for page padding on non-home routes
   - Doesn't provide the "always consistent, always present" header the user explicitly chose
   - Rejects the user's stated preference for full consistency over minimal changes
   - Rejected per the user's explicit decision

## Pattern for future work

When cross-route-tree state or visibility-dependent behavior is needed elsewhere in `apps/web`:
1. If the state is global app state (e.g., auth, theme), it's already handled by existing patterns — use those
2. If the state is specific to a small part of the tree (e.g., a scroll event on one page that affects a sibling component in the layout), use React Context with a Provider wrapping both, following this ADR's pattern
3. Avoid prop-drilling through multiple route components; prefer Context
4. Keep Context focused on a single concern (e.g., hero visibility, not "all home page state")
5. Document the Context's purpose, what writes to it (and from where), and what reads from it in comments

This establishes React Context as the codebase's standard tool for cross-tree communication, avoiding a proliferation of different state-management patterns.
